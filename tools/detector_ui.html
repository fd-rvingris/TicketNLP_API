Loading model…

The Classify ticket tab gives every ticket one primary type and one intent from the taxonomy. Alerts are typed by their alert name, because alerts are templated; wording the taxonomy makes unambiguous is typed by keyword rules; everything else is typed by a local model that learned from tickets Claude labeled, and a close call is flagged as uncertain. Nothing is sent to an API.

  1. 1

    Read the ticket

    The subject and the body, as pasted. The model reads the subject and the first 8,000 characters of the body.

  2. 2

    Is it an alert?

    alert_parser.py

    The alert parser checks the text against the known alert layouts: the collector's table, labeled and Markdown layouts, Grafana firing alerts, backup exception reports and volume capacity checks. If one matches, it reads the alert's family and alert name (for example collector and Long-Running Blocking Chain). If none matches, the ticket goes to the keyword rules (steps 4 and 5).

  3. 3

    Look up the alert name

    57 alert names and patterns, 6,000 alert tickets

    The pair (family, alert name) is looked up in the alert-name table (ticket_analysis/alert_types.json): an exact name first, then name patterns, which cover alert rules whose names carry a client's name. The table says how far the name alone decides the type:

    Name decidesWhat happensAlert names
    YesThe table's type is the answer.51
    PartlyThe table's type is used, with a note that the body can move it. For example, an SQL Agent job failure is scheduled_jobs, but a failed DatabaseBackup job belongs in backup_restore. The page shows the note; it does not apply it.6
    NoThe table's default is used with a warning, because the name names no condition. The largest is errors (2,142 tickets), defaulted to monitoring_tooling until someone checks what those alerts contain.4
    Not in the tableThe keyword rules and then the model decide (steps 4 to 6). When the model decides, a warning says it learned from human tickets only.–
  4. 4

    Strip email boilerplate

    text_clean.py

    A copy of the text for the rules drops external-sender banners, confidentiality footers, image and attachment links, URLs, quoted reply history, standalone greetings and sign-offs with the signature under them, the support mailbox name and @-mentions. A line that also carries a server-shaped name, a SQL keyword or an error number is never removed, and if nothing would be left the raw text is used.

    The model reads the raw text. Feeding it the cleaned text lowered cross-validated type accuracy (74.5% to 73.8%, averaged over five splits), so cleaning is used only for the rules. The server detector never uses it.

  6. 6

    Score with the local model

    ticket_types.py
    • Features: word and two-word phrases (TF-IDF) from the subject and from the body, kept separate.
    • Model: logistic regression, one for the type and one for the intent. It shows its top three of each with probabilities, so a close second choice is visible.
    • Training data: Claude's labels on 600 human tickets sampled across the Zendesk categories. Claude applied the selection rules below when labeling; the model learns them only from those examples.
    • Uncertain flag: when no rule fired, a type whose probability is below 30%, or within 5 points of the second, is marked uncertain. In cross-validation this flags about 30% of the tickets the model decides; those are right about 27% of the time, against about 89% for the rest. The subject carries a lot of weight, so add it when you have it.
  7. 7

    Set the intent

    • Alerts: fix_incident, or provide_information when the alert says the condition cleared, resolved, succeeded or recovered.
    • Everything else: the model's intent.
  8. 8

    Show the result

    The primary type and intent with their definitions, where each came from (alert-name table, keyword rule or model), an uncertain marker with the reason when the model's choice is a close call, the model's top three, and for an alert, the table entry it matched.

The selection rules

How a primary type is chosen when a ticket touches several areas. Claude labeled the training tickets with these rules, and classify.py (prompt v2) gives them to the LLM classifier when an API key is available.

    How accurate is it?

    Measured 2026-10-17 with 5-fold cross-validation on the 600 labeled human tickets (python -m tools.baseline --labels ...), keyword rules first and the model for the rest. The rules are fixed patterns, so no ticket is scored by a model that saw it. Alerts are not in this measure; their accuracy depends on the alert-name table.

    AccuracyMacro F1Model alone, before the rulesAlways guessing the most common
    Type74.0%65.6%73.3% / 65.1%11.3%
    Intent83.2%67.6%83.2% / 67.6%34.7%

    The rules raised access_security F1 from 70.0% to 73.2%; staff_access (94.0%) and database_refresh (44.4%) are unchanged and deployment rose from 78.5% to 79.5%. Reliable: staff_access, service_admin, assessment_review, capacity_storage, backup_restore. Weak: engine_errors, data_request_query, configuration_change, install_migrate_upgrade, database_refresh, which have few training examples. Where Claude itself was less than confident, the classifier is right 56.5% of the time.

    How Claude and the DBAs would work together

    Proposed. Steps marked "not built" do not exist yet.

    1. 1

      Claude labels in bulk

      first pass

      Claude labels new tickets at volume, as today, giving each label a confidence. This keeps the training set large and cheap to grow.

    2. 2

      Choose what DBAs label

      not built
      • Tickets the classifier flagged uncertain, which are right only about 27% of the time.
      • Weak types with few examples: database_refresh, engine_errors, data_request_query, configuration_change, install_migrate_upgrade.
      • Tickets where Claude was less than confident, or where Claude and the model disagree.
      • A small random sample, so the audit of Claude's labels is not biased toward hard tickets.
    3. 3

      DBAs label and correct

      not built
      • Label tickets tab: a type and intent mode beside the existing server mode, with Claude's and the model's answers hidden until the DBA has chosen.
      • Classify ticket tab: a "wrong type?" button that records the correct type.
      • Keystone: when a DBA changes a ticket's type there, Keystone sends the correction to the API's feedback endpoint.

      Every label is a new row with the ticket, the type and intent, the labeler, the time, the taxonomy version and what the model had said. Rows are never overwritten, so any training set can be rebuilt.

    4. 4

      Decide which label wins

      not built
      SituationLabel used for training
      Two DBAs agree, or a reviewer settled a disagreementThe DBA label
      One DBA labeled the ticketThe DBA label, over Claude's
      Two DBAs disagreeNone until reviewed; the ticket goes to a review queue
      Only Claude labeled the ticketClaude's label

      Each Claude and DBA disagreement is also counted, which measures how far Claude's labels can be trusted, type by type.

    5. 5

      Keep an honest test set

      not built

      A fixed set of DBA-labeled tickets is never used for training. Every new model is scored on it, so accuracy is measured against people rather than against the labeler the model learned from.

    6. 6

      Retrain on a schedule

      not built

      Each quarter, a job trains on Claude's and the DBAs' labels combined, scores the new model on the test set, checks every keyword rule is still at least 90% precise, and publishes a new model version only if it is not worse. The previous version stays available for rollback.

    7. 7

      Improve the taxonomy and Claude's instructions

      Patterns in DBA corrections show where a type definition or tie-break is unclear. Those become new rules in the taxonomy notes and in Claude's labeling prompt, so Claude's next batch is labeled better. If DBAs add, split or merge types, that is a new taxonomy version: old labels are mapped where the change is clear and relabeled where it is not.

    8. 8

      Result

      Claude supplies volume, DBAs supply accuracy where it matters most, and every model version can be traced back to the labels and taxonomy it was trained on.

    Dictionary pass (score 1.0) Rules (score 0.95) Model (scored, thresholded) Filtered out Resolution
    1. 0

      Inputs

      • Ticket text: the subject plus the first 20,000 characters of the description.
      • The client, from the Zendesk organization id (or name).
      • The known-names directory per client. Confirmed names come from parsed alert fields and the CMDB export, with the environment the alert gives (collector Environment Name, Grafana env). Names seen only in dw_servers are known but not confirmed.
    2. 1

      Tokenize

      Splits on whitespace and punctuation but keeps \ . - _ , : $ inside a token, so HOST\INST, db01.corp.local, host,1433, tcp:host and MSSQL$INST survive whole. Each token is split into its server-like parts (UNC host, service suffix, port, HOST\INSTANCE), and connection-string values (Server=, Data Source=) are marked.

    3. 2

      Candidate filter

      generous: a name dropped here cannot come back
      • Host candidate: 3 to 63 characters with a letter, or an IPv4 address; not a stop word (built-in list plus words in 0.5% of human tickets), date, ticket number, KB or error code, file name or email part.
      • Instance candidate: 2 to 16 characters with a letter, and a known instance name, within 3 tokens of an instance cue, or written in upper case.
      • new A confirmed host of the client stays a candidate even when it is a frequent word, if it has a digit or punctuation or follows a server word.
      • new A letters-only name known only from dw_servers is not a host candidate unless it sits in a connection string, UNC path or has a port.
    4. 3

      Dictionary pass

      score 1.0new
      • A confirmed host of the client, written alone or as HOST\INSTANCE, is detected outright.
      • A letters-only confirmed host (payroll) also needs a server word before it: server, host, vm, box, machine, node.
      • A confirmed instance name counts only next to an instance cue (the FINANCE instance).
      • One check runs before it: a host the alert names in its own parsed fields is marked host:alert_field (score 0.95).
    5. 4

      Rules

      score at least 0.95
      instance:service_suffix MSSQL$NAME, SQLAgent$NAME
      instance:oracle SID=, SERVICE_NAME=, host:1521/NAME, @host:1521:NAME; SID or PDB NAME when Oracle is mentioned
      instance:name_before_instance NAME instance
      instance:name_after_instance instance (named) NAME
      host:host_instance HOST\INSTANCE, host has a digit or is known
      host:connection_string Server=, Data Source=
      host:unc_path \\host\share
      host:port host,1433, tcp:host, or a database port: host:1433, :3306, :5432, :1521, :27017, exporter :9104
      host:after_server_word server sql01, instance on sql01
      host:known_name client's known host with a digit
      host:near_known_name one typo, or trailing digits differ
      instance:known_name client's known instance in upper case
    6. 5

      Model

      logistic regression: host, instance or none
      • Name: character n-grams 2 to 5 (char_wb, TF-IDF), so an unseen name is judged by its shape.
      • Context: the 3 words either side.
      • Dense features: length, case, digits, punctuation, compressed pattern (L6 D2), port, connection string, UNC, alert or human, how many hosts use the name as an instance, and resemblance to the client's naming convention.
      • Thresholds come from the best F1 on a validation split; the threshold fields on the other tabs start at the saved model's values. A rule or dictionary match lifts the score, so the model decides only the rest.
    7. 6

      Decide and resolve

      • Host or instance, whichever clears its threshold (host wins a tie).
      • Status from the directory: known, new instance on a known host, possible new host, typo of a known name (one edit, same pattern), or a sibling of a known host.
      • A bare instance is paired with the nearest host in the ticket, then with the client's single host that has it; several are ambiguous.
      • new environment from the client's alerts or CMDB export for the resolved host.
